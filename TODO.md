## Direction

sift is a better Gmail filter and spam filter: models work out what mail is, and what they learn is turned into rules so a model is needed less and less. It suggests first and acts second. By default it only observes: every decision is a suggestion, shown in the dashboard. The user teaches it there until it stops making mistakes, and only then lets it act.

## Labels and rules

The model: every message gets a label (what it is); the label carries the outcome (what happens); a rule says what mail is without a model.

Built: labels with defaults and the user's own; outcomes keep, archive, mark spam and block, with "also mark it read" and unsubscribe; three kinds of rule (an action, a label, or an action when the mail is a given label); answers that choose their scope (sender, domain, sender plus words in the subject, or only the waiting mail); the most specific rule wins and one that keeps mail always does; sift proposes rules and writes one itself only for a sender it blocks; both Gmail labels on mail sift acts on.

- [ ] **Three kinds of rule, the rest.** Built: a rule is conditions, then an action (no model, labelled only when another rule names the label), a label, or an action for mail that turns out to be a given label (sift reads each message; anything else from there is judged as usual). `usually` rules became the third kind; trust, unwanted and block are plain action rules; the Rules screen's dialog is written in the order a rule applies (which mail, an address or a domain in one box; only when, in the user's words; the label, or with no label an action) and makes the first two kinds without an action of their own; the third kind and a label rule's own action are left to proposals and older rules; an action rule that archives can be a Gmail filter. Still to do: "labelled when free" does not yet ask the header-checks tier; a condition in the user's own words still needs a label; the sender page says the kinds in sift's words, not yet the user's; decide whether the dialog should make the third kind again; and mail with an action and no label shows a blank where lists and charts expect a label.
- [ ] **The answer, the rest.** Built: an answer says what one message is, does that label's action to it in Gmail (even while observing), keeps it as an example and makes no rule; the toast offers the same for the sender's other waiting mail sift guessed the same way; three answers alike propose a rule; the panel's "Make a rule…" opens the rule dialog on the sender. Still to do: the model gives one label, so "what else it might be" is the sender's history; ask the model for its top two or three with a confidence each and store them with the decision. An answer cannot block or unsubscribe; decide whether those belong on the label only.
- [ ] **Standing, the rest.** Built: every sender and every domain (except ones anyone can get an address at) has a standing. Trusted, unwanted and blocked come only from the user's own rule for exactly them; known and new from how much mail there is. Having written to someone makes them known, not trusted. It is given to the model, shown wherever a sender is named, and set in one press on the sender's or domain's page. Still to do: how much of a sender's mail the user opens or leaves unread; standing that is earned (answers that keep agreeing) as well as given; the pages on a phone, where the mail table scrolls sideways; and a list of all senders and domains to browse by standing.

## Deployment and isolation

- [ ] **Security policies for hosting it for other people.** Write down, then enforce in code, what makes sift safe to run as a service someone else trusts. This is what the hashing in telemetry, the sealed mail and the encrypted credentials below are parts of. To decide and record in one document (`docs/SECURITY.md`), then hold every change to:
  - **Hold as little as possible.** For each thing stored or sent anywhere (database columns, logs, telemetry, the model provider), say why it is needed, for how long, and in what form (plain, hashed, sealed to the user). Anything without a reason goes.
  - **Tenants cannot see each other.** Done: each person's mail is in a database of their own, and the dashboard, the daemon, test runs and re-judging each hold only the one they are for; a test runs every route as two people. Not yet: each person's data is not separately keyed.
  - **A database per person** (done, see docs/ARCHITECTURE.md, State). It has to survive a move to hosting, so it rests on three things any host must give:
    1. A person's database is opened by their id at run time, so adding someone is not a deploy.
    2. Whatever opens it migrates it first, so code only ever meets the schema it shipped with. Nothing migrates databases from outside.
    3. One writer per person at a time, which also runs their passes.
    - **SQLite, and only SQLite** (decided 2026-11-15). Postgres would keep people apart only by row-level security, which is not acceptable here, or by a database or schema per person, which migrates per person just as files do and adds a server to run (PGlite is not proven as the only copy of someone's mail). Vercel goes with it: it keeps no disk.
    - **Hosts.** Machines with local disks, each person routed to the one holding their file, backups streamed to object storage (Litestream). Cloudflare Durable Objects, below. D1 fails 1 and 2: databases are bound at deploy and migrated from outside, so across tenants code and schema drift apart and every change becomes expand, backfill, contract.
    - **So Durable Objects stay possible.** One object per person holds their SQLite and runs their passes on an alarm, and a dashboard request about their data is forwarded to it. Each object runs one code version at a time and migrates in its constructor. What the code already does for it: everything that reads or changes someone's data takes their database; transactions go through `Sql.transaction` and await only the database; `schema_migrations` is the only record of what has run, and PRAGMAs stay in the file adapter. Still to do:
      - Migrations ship as modules the code imports: a Worker has no file system. `migrate()` already takes them as a list; `readMigrations` reading a folder is the file adapter's.
      - `Sql` over `ctx.storage.sql`, with `transactionSync`, and a Store whose `user(id)` is that person's object.
    - **Still to do here:** copy each database (`VACUUM INTO`) before migrating it, so a failed or unwanted migration can be undone by hand; and a key per person's file, with encryption at rest.
  - **What the operator can see.** With sealed mail and hashed telemetry, say plainly what someone running the service can and cannot read, and make the claim checkable.
  - Goes with: keeping people apart (Dashboard), sealing stored mail, Sentry, and the one-click deploy.
- [ ] **Seal stored mail to a key only the user holds.** Decided 2026-11-15: message content sift keeps (`suggestion_bodies`, `examples`) is encrypted so the server cannot read it back. The cost is accepted: sift cannot re-analyse stored mail by itself.
  - **How.** The browser makes a key pair when the user sets a passphrase in the dashboard. The server keeps the public key and seals each body to it as it arrives (it has the text at that moment, from Gmail, and never again). The private key stays in the browser, and a copy wrapped with the passphrase is kept on the server so a second device can unlock with the passphrase. Reading a message decrypts in the page.
  - **What it changes.** Search over message text is not possible. Replaying examples through a model (the evals) and using them as few-shot examples need the page to be open and unlocked to hand the text over for that run, or use only what is not sealed (sender, subject, headers, label).
  - **Not covered.** Metadata (sender, subject, headers, reasons) stays readable, because rules and every list need it; whether to seal subjects too is open. A lost passphrase loses the stored text and nothing else.
  - Per-account keys go with keeping people apart.
- [ ] **One-click deploy to Cloudflare**, for people who do not want to run a machine. After model sign-in has moved to the dashboard, so the whole setup can happen in a browser. sift today is one long-running process with SQLite files and credentials on disk, and Workers offer neither, so this needs:
  - **Storage through `Store`**: `user(id)` answered by a Durable Object per person (a database per person, above). Tokens and secrets in the platform's secret store instead of files in the home directory.
  - **Passes on a schedule.** Each user's object wakes itself on an alarm instead of a loop, each pass fitting inside the time limit, or Gmail push through Pub/Sub. One pass at a time per account must still hold.
  - **Setup in the browser.** No `sift init`: the Google client, the model sign-in and settings all entered in the dashboard, with the first visitor claiming the install safely.
  - **A public address.** It would no longer sit behind a tailnet, so sign-in is the only gate; review the session and write protections with that in mind, and decide on encryption at rest first.
  - **Runtime differences.** Cloudflare Workers are not Node: check what sift uses (`node:sqlite`, `node:https`, the model library) against Workers.
- [ ] **Sentry, with tracing.** Errors and OpenTelemetry spans for a pass, each message's triage (one span per tier, the model call with tokens and cost), each mailbox change and each dashboard request. Nothing that identifies mail leaves the machine: no message content, subjects, sender names or sender addresses; only the connected account's own address identifies a span. Everything else is referred to by a keyed hash (sender, domain, message id), the same hash everywhere so traces can be joined to each other and looked up locally; decide whether to store the hashes in the database to make that lookup cheap. A scrubber on the way out as a second line of defence, the DSN in `sift.toml`, and off unless set.
- [ ] Restrict the core container's egress to Google and the model providers. The unsubscribe request is the one call to an arbitrary host and needs a relay container of its own first; the plan is in [docs/DEPLOY.md](docs/DEPLOY.md).
