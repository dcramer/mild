## Direction

sift is a better Gmail filter and spam filter: models work out what mail is, and what they learn is turned into rules so a model is needed less and less. It suggests first and acts second. By default it is off: every decision is a suggestion, shown in the dashboard. The user teaches it there until it stops making mistakes, and only then turns it on.

## Labels and rules

The model: every message gets a label (what it is); the label carries the outcome (what happens); a rule says what mail is without a model.

Built: labels with defaults and the user's own; outcomes keep, archive, mark spam and block, with "also mark it read" and unsubscribe; three kinds of rule (an action, a label, or an action when the mail is a given label); answers that choose their scope (sender, domain, sender plus words in the subject, or only the waiting mail); the most specific rule wins and one that keeps mail always does; sift proposes rules and writes one itself only for a sender it blocks; both Gmail labels on mail sift acts on.

- [ ] **Three kinds of rule, the rest.** Built: a rule is conditions, then an action (no model, labelled only when another rule names the label), a label, or an action for mail that turns out to be a given label (sift reads each message; anything else from there is judged as usual). `usually` rules became the third kind; trust, unwanted and block are plain action rules; the Rules screen's dialog is written in the order a rule applies (which mail, an address or a domain in one box; only when, in the user's words; the label, or with no label an action) and makes the first two kinds without an action of their own; the dialog makes the third kind too ("When it is", then an action), which "Keep as …" in the message panel starts on; a label rule's own action is left to older rules; an action rule that archives can be a Gmail filter. Still to do: "labelled when free" does not yet ask the header-checks tier; a condition in the user's own words still needs a label; the sender page says the kinds in sift's words, not yet the user's; and mail with an action and no label shows a blank where lists and charts expect a label.
- [ ] **The answer, the rest.** Built: an answer says what one message is, does that label's action to it in Gmail (even while sift is off), keeps it as an example and makes no rule; the toast offers the same for the sender's other waiting mail sift guessed the same way; three answers alike propose a rule; the panel's "Make a rule…" opens the rule dialog on the sender and the message's label. Still to do: the model gives one label, so "what else it might be" is the sender's history; ask the model for its top two or three with a confidence each and store them with the decision. An answer cannot block or unsubscribe; decide whether those belong on the label only.
- [ ] **Standing, the rest.** Built: every sender and every domain (except ones anyone can get an address at) has a standing. Trusted, unwanted and blocked come only from the user's own rule for exactly them; known and new from how much mail there is. Having written to someone makes them known, not trusted. What the dashboard shows after a name is not standing but how you know each other (`contactOf`): new, you write to them, or never answered. It is given to the model, and given on the sender's or domain's page through the rule dialog, started on what that standing does, and taken back in one press. Still to do: how much of a sender's mail the user opens or leaves unread; standing that is earned (answers that keep agreeing) as well as given; `standingOf` counts a label rule whose label archives as Unwanted, so the sender page lights a standing only for an action rule for exactly them (the server should agree); and a list of all senders and domains to browse by standing.
- [ ] **Unsubscribe, the rest.** Built: unsubscribe is an extra, like mark read, that a label or a rule carries; of the default labels only Cold outreach has it on; sift makes the sender's one-click request after the mailbox change succeeds, only while sift is on, never for someone the user has written to, and leaves a sender alone for a week after a failure. Not yet run against a real list. Still to do: lists that need an email sent or a page opened are skipped, so show their link for the user to open; show on the Labels and Rules screens how many senders each has unsubscribed from; and say plainly, before sift is turned on, that these labels will start unsubscribing.

Declined because it does not buy what was wanted: client JavaScript went up (205 kB gzip for one route against 179 kB for the whole app), the screens are client-dynamic anyway, it is one to two weeks across every view, and it adds standing risk. Revisit only if hosting for other people needs it, and then with these in hand:
  - **Credentials.** A loader runs inside the sift process, next to the Gmail tokens, model keys and session secret. Anything a loader returns is serialised into the page, so one careless return ships a secret to the browser; and server code and browser code live in the same files. Today the boundary is a wall: the page can only reach what `/api/` chooses to send. Server rendering needs that wall rebuilt on purpose (a lint rule on what loaders may import, a serialisation allow-list, tests that grep rendered HTML for secrets).

  - Shared parts that break when rendered on a server: dates and numbers format in the server's locale and time zone (`lib/format.ts`); `system/copyable.tsx` and `views/sign-in.tsx` read `navigator` and `window` while rendering; the chart and tier swatch set inline styles.

## Inference tier
