# Architecture

sift polls Gmail for new inbox mail and decides, per message, a **disposition** (`keep`, `archive`, `spam`, or `review`) and independently a **subscription action** (`preserve` or `unsubscribe`). It is designed so that most mail never reaches a language model.

## Labels, rules and the cascade

Two things are decided about every message, and they are kept apart.

- **What it is: a label.** Each account has one list of labels (`labels`), seeded with cautious defaults and added to by the user. A label has a name, a description the model reads, a Gmail label, and an action.
- **What happens** is the user's to say, never a model's. Usually it is the label's action, one of keep, archive, mark spam, or block; a rule can name an action itself. Beside the outcome a label can carry extras: mark read (with keep and archive) and unsubscribe. A rule can add either for the mail it decides. "Leave it for me" is not an action: sift suggesting instead of changing Gmail is a matter of trust, and the only time mail is held for the user is when no tier could place it or a protection stopped sift.
- **Block** is sift's own, since Gmail's block list is not in its API ([GMAIL.md](GMAIL.md)): the message is marked spam, and once that has happened a rule is written so the sender's later mail is that label without a model. Only when the message passed DMARC, so an impersonated sender is not the one blocked, and never for someone the user has written to. A rule may carry the user's own exception to its label's action ("this one is a newsletter, but keep it").

A label's id and Gmail label never change after it is made, so renaming one orphans nothing. An account has at most twelve labels (`MAX_LABELS`): each is a choice the model weighs on every message and the user answers with, so a long list makes both worse.

Tiers run cheapest first. A tier either names a label or abstains; the first answer wins.

| Tier | Where | Cost | Status |
| --- | --- | --- | --- |
| 1. Gmail filters | Gmail itself; runs even when sift is down | none | built: a rule is copied there when the user asks ([Rules as Gmail filters](#rules-as-gmail-filters)) |
| 2. Rules | `src/triage/stages/rules.ts` | none | built and wired |
| 3. Decision model (Jev / Clef via pi-ai `classify`) | `src/triage/stages/classifier.ts` | ~$0.0001 per message | stage built, provider not wired |
| 4. Model | `src/triage/stages/model.ts`, `src/model/` | one model call | built; in use with sift off, with a ChatGPT subscription model |
| Fallback | `src/triage/pipeline.ts` | none | built |

Every message is meant to be one of the labels. When the model cannot tell which (its "unsure"), the answer is `review`: the message stays where it is, gets the review label, and the user is asked which label it is, or adds one. A model call that fails (a provider error, or an answer that is not a usable verdict) is not "unsure" and decides nothing: the message stays in the triage queue and is asked about again on the next pass. After three tries that failed on its own account it leaves the queue (`MAX_ATTEMPTS`, `src/store/runs.ts`) and shows in Activity's Failed view as not judged, with the last error, until the user puts it back (one at a time, or all at once) or says what it is there; it never becomes a suggestion. A try counts when no decision came of it: an unusable answer, a provider error while the model answers other calls in the same pass, a call a stopped pass never finished (it is recorded as started before it is made), or a billed verdict whose decision was never recorded. Provider errors that say nothing about the message do not count (they are stamped `retried_at`): three in a row stop the pass asking the model, since the provider is likely down, and errors in a pass where the model answered nothing are an outage too. After that stop, mail that needs the model stays queued, unrecorded, rather than going to a rule that would have deferred to it; mail a rule decides by itself still is. Each call is one attempt with a 60-second timeout and no retries inside the provider's SDK (`src/model/judge.ts`), so a hung call cannot hold up a pass and every attempt is a run of its own. With no model connected, mail no rule covers is not decided at all: it stays in the triage queue (newest first, so it never holds up new mail) and is neither a suggestion nor changed, until a model is connected or a rule comes to cover it.

**A rule** is conditions, then a label, an action, or both. There are three kinds, and a sender or domain can have one of the first two and any number of the third:

- **Conditions → action** ("from this notifications address: archive"). No model. sift does not say what the mail is unless that costs nothing: another rule that matches names a label. A sender's standing (trusted, unwanted, blocked) is this kind of rule.
- **Conditions → label**, optionally with its own action in place of the label's. No model.
- **Conditions, when it is label L → action.** It cannot apply until a tier has said what the mail is, so when it is the best match the rules tier steps aside for the tiers that name labels, and `settle` applies it to their decision: the tier's label stands, the rule says what happens. Mail from there that turns out to be something else falls to the sender's rule for all their mail if there is one, and otherwise is as the tier said. With no action of its own it confirms the label's as the user's wish, which is what answering "right" for a sender makes when the label would hide their mail.

A rule can also carry a condition in the user's own words, which only a model can apply; it needs a label for the model to answer with. Rules come from the user (`user`), from the user correcting a suggestion (`correction`), or from sift itself (`learned`), only when it blocks a sender. Otherwise sift proposes: a rule for a sender whose last five messages a model gave the same label, and dropping the "when it is L" from a rule once ten messages in a row were L.

There is no tier built into the code that decides what mail is: what decides is a rule the user can see and change, or a model. A message's facts (`src/triage/facts.ts`) are recorded, given to the model, shown when a message is opened, and are conditions a rule can have ("from anyone at this domain, that is not a reply").

Rules that matter across tiers:

- A rule that keeps all the mail it matches is a protection and beats any other rule. Otherwise the most specific rule wins (more conditions, then an exact sender over a domain, then a rule that waits for a label over one that does not), so "this sender when the subject contains X" beats "this sender" whichever was written first. A condition on a fact weighs half of one on the sender, the recipient, the list or the subject, since one fact ("is a reply") takes in mail from anyone: "this domain" beats "is a reply", and "this domain, that is a reply" beats both.
- A rule sift made itself (it does so only when it blocks a sender) never hides mail from someone the user has written to; the user's own rules do what they say.
- A rule whose label has been removed does nothing.
- Mail an action rule decides may carry no label at all: decisions, lists and Gmail (which then gets only the mark of what sift did) all allow for that.
- Spam has a higher confidence bar than archive.
- Errors abstain, and a failed model call decides nothing. Nothing fails toward a mutation.

## Message facts

Every tier, the prompt and the dashboard read one named set of facts about a message (`Facts`, `src/triage/facts.ts`) instead of each re-reading headers.

- **From headers and labels, at sync:** unsubscribe header and whether it is one-click, mailing list id, marked bulk, marked auto-generated, the DMARC, SPF and DKIM results, the bulk mail service it went through (from who signed it, its envelope sender and the services' own headers), whether replies go elsewhere, whether the owner is in To, in Cc or in neither (any of their addresses: the account's, with or without a `+tag`, its dot-variants on gmail.com and googlemail.com, and its Gmail send-as addresses, read on the first sync of each day and kept in `mailboxes.aliases`), whether it is a reply, and Gmail's category tab.
- **From the whole message, when a model is about to judge it:** whether it has attachments and, from the HTML part (`src/triage/html.ts`), whether it carries a tracking pixel (a remote image drawn 1×1 or hidden), how many sites it links to, whether most links pass through a click-tracking redirect, and whether any link goes to the sender's own domain. These mark campaign mail even when the headers do not. The HTML is read and dropped, never stored, and nothing in it is fetched. Mail a rule decides is read whole only while some rule asks about attachments or a tracking pixel; otherwise it has none of these.
- **From the thread, for a reply a model is about to judge:** how many messages came before it and whether the owner sent one of them (`users.threads.get`, labels only: a message the owner sent carries `SENT`). No other message's content is read or stored.
- **Recorded** in `messages.facts`, rewritten when the whole message or its thread adds to them, and returned with a message's detail.
- **Rules match on them** (`RuleMatch.facts`): each condition is one of the answers `RULE_FACTS` offers for a fact, held by `matchesFacts` against what is recorded, and a fact not known for the message fails its condition. Offered: a one-click unsubscribe, a mailing list, marked bulk, a bulk mail service, DMARC, replies going elsewhere, how the owner is addressed, a reply, Gmail's category, attachments and a tracking pixel. Left out: counts, the list id (a rule names that), SPF and DKIM (DMARC is the one that proves a sender), and "no tracking pixel", which mail with no HTML could never match. A rule that asks about attachments or a tracking pixel needs the message read, so while one exists each message is read before the rules, model or not, and once for the rules and the model together. A rule with a fact condition cannot be a Gmail filter (Gmail cannot see facts), and anything that acts on a sender's address still needs DMARC, as everywhere.
- **Lists narrow by them.** Suggestions and Activity filter on a few (`FACT_FILTERS`, `src/dashboard/types.ts`) in SQL on `messages.facts` (`factsWhere`, `src/store/messages.ts`), which a GIN index serves.
- **Only what can be checked.** Whether mail reads as AI-generated, and its language, are judgements for a model, not facts.

## Learning loop

Decisions flow back down so the same mail is cheaper next time.

1. sift proposes a rule when the same thing keeps happening for a sender (a model's decisions agreeing, or the user's answers), and the user accepts or dismisses it. Accepting opens the rule dialog started on the proposal; the proposal is resolved only by a rule made there (`proposal` on `POST /api/rules`, one transaction), as the user left it. Accepting "stop reading them" first says what the rule does now and what it will do. sift writes one by itself only when it blocks a sender.
2. A rule that Gmail can express is copied to a Gmail filter when the user asks for it. sift does not promote one by itself.
3. Corrections are detected from Gmail history: the user moving a message back to the inbox or out of spam, archiving or marking as spam what sift kept, or changing its `sift/…` label, is their answer for that one message ([Teaching](#teaching)). It never makes or changes a rule by itself.

## Layout

```
src/
  cli/        main.ts parses and dispatches; commands/ has one module per command (init, run, status, dev, dashboard)
  config.ts   data directory and paths
  secrets.ts  encrypts the credential files with a key from the environment
  store/      the only module that opens a database: Postgres or PGlite (db.ts), the per-person handle (sql.ts) and its hold on each query (own.ts), what queries are written with (query.ts), the Drizzle schema and its migrations, queries
  triage/     pure pipeline: types, header features, stages
  actions/    the only mutation path: executor, undo, decision-to-action planning, Mailbox port, filter validation
  gmail/      the only module that holds the Google token: OAuth, API adapter, history sync
  dashboard/  the server for the built web app and its JSON API: api/ (one module per resource), queries/ (what they read), scope.ts (whose data a request may see)
  daemon/     orchestration: sync pass, triage pass, and the `sift run` loop
  learn/      what the user teaches: suggestions and answers, and answers read from what they did in Gmail
  model/      the only module that talks to model providers (pi-ai): login, credentials, the classifier call
web/          the dashboard page: React, Tailwind, its own design system on Base UI; builds to web/dist
tests/        synthetic fixtures only
docker/       Dockerfile and compose file; upgrade, backup and restore are in docs/DEPLOY.md
```


Boundaries are enforced by lint; see [AGENTS.md](../AGENTS.md).

## Gmail

- **Scopes:** `gmail.modify` and `gmail.settings.basic` (`src/gmail/scopes.ts`). Both are restricted scopes, so each user brings their own Google Cloud project with a Web application OAuth client; sign-in is the authorisation-code flow with PKCE, started from the dashboard. Left in "Testing", Google limits sign-in to listed test users and ends it every 7 days.
- **Tokens:** each mailbox's refresh token is kept in its person's own database (`credentials`), encrypted when a key is set and bound to that person and mailbox ([SECRETS.md](SECRETS.md)). Only `src/gmail/` uses it; the process that starts sift reads it and hands it over.
- **First connect:** sift records the current history id and handles mail from then on. It never sweeps the existing inbox unasked.
- **Sync is separate from triage:** a sync pass records message metadata and then advances the cursor; triage works from recorded messages that have no decision yet. Messages are recorded 50 at a time as they are fetched and the cursor moves with the last, so a failed fetch leaves the cursor in place and the next pass reads the same history but fetches only what is not yet recorded.
- **Quota:** every Gmail call waits its turn under its mailbox's share of Google's 6,000 units a minute (`pacer`, `src/gmail/quota.ts`) rather than failing on a 429. The count is in the ephemeral store, so every instance shares it.
- **Change detection:** poll `users.history.list` from the stored `historyId` (2 quota units per call, against 6,000 per user per minute). A 404 means the cursor expired: read the new cursor, then search the last 7 days of the inbox. History also carries every label change, sift's own included and with no word on who made it, so `userChanges` (`src/learn/gmail.ts`) cancels each change in sift's `actions` log since the previous sync began against one matching entry; what is left is the user's. Label changes made while the cursor was expired are lost. Pub/Sub push is a possible opt-in; it still needs the polling fallback.
- **Reads:** `format=metadata` with named headers for triage. The body is fetched only for the agent tier, for the text of mail waiting on the user, and for the HTML of a message open in the dashboard (`getMessageHtml`), which is shown and not kept.
- **Archive** is per message. Gmail shows a thread in the inbox while any message in it has `INBOX`, so a thread stays visible until each message sift was given has been handled; sift does not act on sibling messages it did not triage.
- **Filters:** at most 1,000 per account, one user label each, no update (delete then create), and they act on new mail only. `validateFilter` rejects forwarding, trash, spam and mark-read actions, criteria with no positive match, and a filter for a rule with fact conditions. See [Rules as Gmail filters](#rules-as-gmail-filters).
- **Unsubscribe:** RFC 8058 one-click only (an https `List-Unsubscribe` target plus `List-Unsubscribe-Post`), and only when DKIM passes. Never a GET, never a link from the body, never `mailto:`. It is the one request sift makes to an arbitrary host, so it runs in a deterministic executor; the agent can request it but never sees the URL.

## The run loop

`sift run` is the one long-running process: it serves the dashboard and, every minute or when woken, sends a pass job for each mailbox: settle unconfirmed actions, sync, then triage every recorded message that has no decision. Upkeep (old examples, message text and messages) is a job per person, sent at start and once a day.

- **Jobs** (`src/daemon/jobs.ts`) are shaped for a hosted queue such as Vercel Queues: ids only, never mail, and safe to deliver twice. Locally they run in-process, four at a time, a job never queued twice while it waits. A pass first claims its mailbox in the ephemeral store (`lock:pass:<mailbox>`, 15 minutes); one that cannot does nothing, so a job delivered twice or sent again while it runs never acts on the same mail at once. Two processes share claims only through Redis.

- **Off is the default.** Whether sift is on is each person's own (`preferences.active`), switched under Settings, and a pass changes a person's mailboxes only while it is on. While it is off, decisions are recorded as suggestions (`carry_out` false) and the mailbox is not touched; a suggestion is never carried out later. The one exception is the user's own answer from the dashboard: it is recorded with `carry_out` and `by_user` and carried out on the next pass whether or not they have sift on, since they pressed it. Nothing else is carried out while sift is off, not even a decision left over from when it was on.
- **Decide, record, then act.** The decision row is written before any mailbox change. Its `outcome` then records what happened: `none` (nothing needed doing), `done`, `skipped` with the reason (left the inbox, spam refused), `failed` or `unknown`.
- **Nothing is dropped.** If the change cannot even be attempted (a provider error), the decision stays unsettled and the next pass retries it. A pass decides each message once; a waiting suggestion gets a further decision only when a rule or a label changes (see Teaching).
- **One account failing does not stop the others.**

## Actions

`src/actions/executor.ts` is the only code that changes a message. Each change follows the same steps:

1. Settle any earlier action on the message whose outcome was never confirmed.
2. Read the message's labels fresh. If it is gone or no longer in the inbox, do nothing.
3. Write the intended change and the original labels to the audit log as `pending`.
4. Send one atomic label change containing only what differs, so unread state and unrelated labels are untouched.
5. Read the labels back and record `done` or `failed`. If the call itself errored, record `unknown`.

`unknown` and `pending` actions are settled by `reconcile`, which reads the mailbox and never replays the change. **In Gmail a message sift acts on gets two labels:** the one for what it is (`sift/newsletters`) and, when sift moved it, one for what sift did (`sift/did/archived`, `sift/did/spam`). The executor adds the second itself, so anything sift moved can be found in Gmail whatever the caller passed. Mail left for the user gets `sift/review`. Spam is refused unless the sender is known and a search shows the user has never written to them; a failed search also refuses.

Undo reverses exactly what the action changed, keeps anything the user changed afterwards, refuses trashed mail, and is itself an audited action.

## Rules as Gmail filters

A rule can also be written to Gmail as a filter, so it applies when sift is not running. Only when the user asks, per rule, and only while sift is on.

- **Which rules.** `filterFor` (`src/triage/filter.ts`, pure) says whether a rule can be one, and why not. A filter runs before sift sees the message and knows none of sift's other rules or protections, so a rule qualifies only if the filter could never do what sift itself would not have done. Refused: a rule that is judged (`usually`, or with a `when`); one whose outcome is spam (not documented for filters) or that marks read (`validateFilter` does not allow it); one matching a list id, asking about a fact, or carrying exceptions; one sift learned that archives, since a filter cannot spare people the user has written to; one whose values could change the meaning of a Gmail search; and one that another rule could overrule for the same mail (a keep rule, a judged rule, or a narrower one).
- **Where Gmail differs.** A recipient condition also matches Cc and Bcc; subject words match whole words, not substrings; a domain is written `@domain`. The verdict lists these (`differs`) so they can be shown before the user asks.
- **Archived by a filter means unseen by sift.** Sync records mail that arrives in the inbox. Mail a filter archives is not recorded, counted against the rule, or unsubscribed from.
- **Writing and removing** go through `src/actions/rule-filters.ts`: validated, written to `actions` first (`filter`, `unfilter`, with no message), then read back from Gmail's list. A filter the account already has that does exactly the same is taken over, since Gmail refuses a duplicate. Removing a rule removes its filter first.
- **Keeping track.** At most every 15 minutes a pass lists the account's filters and records on each rule (`filter_state`) what it found: `active`; `changed` (edited in Gmail: left alone); `gone` (deleted in Gmail: not put back); `outdated` (the rule, its label or another rule changed, so the filter no longer does what sift would). An outdated filter is replaced, or removed if the rule can no longer be one, while sift is on; while it is off it is only marked, and keeps running in Gmail.

## Preferences

Everything a person prefers is in their own database.

- **Whether sift is on, and their model** (`preferences`, `src/store/preferences.ts`): whether sift changes their Gmail or only suggests, and which model judges it, both set under Settings. What they want is said by their labels' descriptions and their rules; there are no free-form guidelines beside them, since the system's intent is the same for everyone and a label's description already says what belongs in it.
- **What is structured or learned:**
  - `labels`: what mail can be and what to do with each. Seeded with cautious defaults (nothing is marked spam); changed and added to in the dashboard, under Labels.
  - `rules`: what the user has said happens to mail, or what it is; and a rule for each sender sift blocked.
  - `correspondents`: whether the user has ever written to an address, cached.

## Model tier

When no rule decides a message, one model call does. It is deliberately not an agent.

- **The model has no tools and takes no action.** Deterministic code gathers the evidence first: the message's facts, the body (fetched on demand, truncated, never stored), how much mail this sender has sent, what was done with it, and whether the user has ever written to them.
- **Its only output is a label** from the user's list, or `unsure`, with a one-line reason. The reply is validated; anything else is a failed call, which is tried again on a later pass.
- **The label's action decides the outcome**, so the user's choice, not the model, determines what happens to the message.
- **Three protections apply whatever the model says:** mail from someone the user has written to is never archived or marked spam on the model's word (and "could not check" counts as yes), nor is a reply in a thread the user has written in, and `unsure` or an unknown category leaves the message for review.
- **It is shown a few of the user's own answers.** Beside each message go up to six stored examples, chosen for it: from the same sender first, then the same domain, then the newest of each label, within a budget of about 1,200 tokens (`src/triage/fewshot.ts`). Each is only sender, subject, the first 300 characters and the owner's label, fenced as untrusted like the email itself, with every field JSON on one line so an example's text cannot close its fence or forge a label. It is always on; a test run can leave examples out, to measure what they add.
- **The prompt marks the email as untrusted** and keeps it apart from the labels and the header facts. The worst an injected email can do is get itself given the wrong label, which the audit log can undo.
- **Learning:** once a model call has given a sender's last five messages the same label, and each ended the way that label says, sift proposes a rule for the sender (`src/store/proposals.ts`); nothing changes until the user accepts it. Each message counts once, by its current decision, and only when that came from a model call: an answer, or decisions made again after a rule or label changed, do not add up to a rule. A sender who already has a rule is left alone.

Models are reached through pi-ai (`src/model/`, the only module that imports it). **Each person signs in and chooses their own,** under Settings, so their mail is judged on their account and at their cost; a pass builds each person's tier from their database (`openModelTier`, `src/cli/controls.ts`). Without a model, mail no rule covers waits, undecided, for one. The ways in (`modelChoices`) are ChatGPT and an API key for OpenAI, Anthropic, OpenRouter or Vercel AI Gateway. An install signs people in to ChatGPT one way, its `chatgpt.sign_in` setting (`SIFT_CHATGPT_SIGN_IN`). By default it is a device code (`openai-codex`): the page shows a code to enter at OpenAI, nothing has to come back to this server, and calls go to Codex's backend at `chatgpt.com`, which OpenAI does not document for other tools. sift asks for the code and checks whether it was entered itself, once per job (`chatgpt-sign-in`), the way pi-ai's own login does in a loop, and stores the credential in pi-ai's shape. `redirect` is OpenAI's Sign in with ChatGPT (decided 2026-11-15), on its documented API at `api.openai.com/v1`, billed to the person's plan. It needs no app registered: each sign-in registers its own client, under the install's device id. But OpenAI only ever sends the browser back to `http://127.0.0.1:1455` on the person's machine, never to a hostname, so the person lands on a page that does not load and pastes its address into the dashboard. sift listens on no port for it: pi-ai's own login does, so sift builds the sign-in and exchanges the code itself (`startChatGPTRedirect`) and stores the credential in pi-ai's shape, which pi-ai then refreshes. A sign-in takes the address for 10 minutes, and a wrong one can be followed by the right one. It is registered as its own provider, `chatgpt`, so it can sit beside an OpenAI key; pi-ai recognises a ChatGPT token only on its `openai` provider, so `chatgptProvider` sends each call as that provider's. Only the install's way is registered, so switching signs everyone out of ChatGPT. The two resellers list hundreds of models; only the major labs' small ones are offered (`offerModel`). One provider is in use at a time. Changing it signs in to the new one beside the old, chooses its model, and only then signs out of the old, so a model is in use throughout. Until a model is in use and signed in, every screen of the dashboard is those steps, on the sheet sign-in uses (`ModelWall`, `web/src/components/model-wall.tsx`): the first time, followed for the owner by pulling in recent mail to answer; when the model in use is lost (its sign-in removed or expired), under "No model connected". Without one there is nothing to suggest, and the screens would only show it. Settings is a panel over any screen, the wall included (`?settings=1`, from the account menu or under the wall), so nothing has to be finished to reach it. Sign-ins are kept in the person's database, through a port (`SignIns`, `src/model/credentials.ts`) so `src/model/` never touches the store. Keys in the environment are never used: they would speak for everyone. Adding a provider means adding it in `openModels` and to `modelChoices`. pi-ai depends on every provider's SDK; the ones sift cannot call (AWS, Google) are removed from the install by `overrides` in `pnpm-workspace.yaml`, so a new provider may also need its SDK put back there. pi-durable is not used: a triage run is one call, and the message queue in the database already gives retry and decide-once.

There is no shell and no filesystem here. A sandboxed agent with those is planned only for a possible operator-facing assistant that does open-ended analysis.

## The command line

Four commands: `init` sets sift up, `run` reads and classifies mail and serves the dashboard, `status` says what is set up, and `dev` is `run` for working on sift. `dashboard` serves the dashboard without reading mail. Everything else (rules, labels, the log of changes, undo, choosing a model) is in the dashboard and has no command. Options are in [CLI.md](CLI.md).

## Home directory

Everything sift keeps is in one directory, the home: `~/.config/sift` by default (`$XDG_CONFIG_HOME/sift`), or wherever `--home` or `SIFT_HOME` points (the Docker image uses `/data`). Keeping settings, guidance, the database and credentials together means it can be backed up or moved as a unit. No setting requires an environment variable, with one exception: the key that encrypts the credentials. Each can be given in one instead (`ENVIRONMENT`, `src/config.ts`, read by the same checks as the file), and the environment wins; a value from it is never written into `sift.toml`, and the dashboard refuses to change it.

- `sift.toml`: settings, only what a deploy must say (`dashboard.port`, `dashboard.host`, `dashboard.allow`, `database.url`, `database.migration_url`). Parsed strictly: an unknown key or wrong type is an error. Command-line flags override it for one run. What a person chooses is in their `preferences`; how often sift looks and how long it keeps things are constants in the code.
- `database/`, `database.lock`: the database, when it is PGlite (see State).
- `google-client.json`, `dashboard-key`: the install's Google client and the session secret, owner-only. People's sign-ins are in their databases.
- `device-id`: names this installation to a subscription sign-in. Not a secret.
- `.env`: optional. Read at start, before the one in the working directory; neither replaces a variable already set.

**Credentials are encrypted with a key from the environment** (`SIFT_KEY`), because a key stored beside them would protect nothing. See [SECRETS.md](SECRETS.md).

- Every one is encrypted and decrypted through `src/secrets.ts`, which knows ciphertext and nothing about what is inside. Each is bound to what it is for (a file's name; a row's person, kind and key), so it cannot be moved into another's place.
- Each value records the id of the key that encrypted it. `SIFT_OLD_KEYS` are accepted for reading; a value is re-encrypted with the current key whenever it is written, and `sift run` re-encrypts all of them at start, in files and in every person's database, and encrypts any still plain, so an old key can be retired.
- A credential whose key is missing stops `run`, `dashboard` and `status` at start, naming it. The alternative is a sign-in that stops working for no visible reason.
- Without a key sift runs as before, storing them plain, and says so at start.
- The rest of the databases is not encrypted; see TODO.md.
- `setup.json`: how far `sift init` has got, so it resumes.

`sift init` (`src/cli/init.ts`) sets all of this up. A first run walks through every step, and one stopped part-way carries on with what is missing. Once the dashboard has an address and the Google client is finished, it instead lists the steps with what each is set to and redoes the one the user picks. The key and the sign-in list are optional, so leaving them unset does not bring the walk-through back. The model is not here: each person signs in to their own in the dashboard.

## Teaching

sift suggests first and acts second. While it is off, every decision is a suggestion, and the dashboard's Suggestions view is where the user teaches it.

- **A suggestion** is the current decision for a message, recorded as a suggestion, that the user has not answered. Decisions that only repeat what the user already said (their answers, marked `by_user`, and rules they wrote or made by correcting sift) are not suggestions; ones from a rule sift learned are.
- **Suggestions are listed one per message**, newest first. The answer is a dropdown that starts on the label sift gave, with a meter for how sure it is (a rule is sure; a model gives a number), and a check that commits it. The dropdown lists what else it might be first: the labels the sender's other mail has had, most first, then every other label. The model gives one label today, so the sender's history stands in for its runners-up.
- **An answer says what one message is, and that is all it says.** Like a spam button with more outcomes: sift records the label, does what that label does to the message in Gmail (see Off is the default), and keeps the message as an example the model is shown next time. It makes no rule. When the sender has other mail waiting that sift guessed the same way, the dashboard offers the same answer for those in one press. Mail the model could never judge is answered the same way from its panel: the answer is its first decision, recorded as an answer to mail sift had no suggestion for.
- **Every answer is scored.** `feedback` records right, wrong, or "answered" (sift had no suggestion, which is not a mistake), per decision. The summary the home page reads reports it for the window per tier and per label, with which labels sift took for which.
- **Rules come from proposals and the Rules page, not from answers.** After three answers in a row giving a sender's mail the same label, sift proposes a rule for that sender (`proposeFromAnswers`), as it already does after five model decisions that agree. Every press that makes or changes a rule opens the rule dialog in place, started on everything that place knows (`web/src/lib/rule-start.ts`): a proposal's sender and label, a message's sender and label, a fact row's sender and fact, a list, a standing's sender or domain and action. The user sees and changes it before adding. Adding replaces the rule with exactly the same conditions, if there is one, and the dialog names it. Taking a standing back is one press. The answer endpoint still takes the wider scopes (`label`, `sender`, `domain`, `subject`), which make rules; the dashboard sends only `once`.
- **Any decision can be answered, not only a suggestion.** Every list opens a message in the same panel: sift's label as the answer to agree with, what else it might be, its reason, the message, and what sift knows about the sender. Answering a message sift had already decided records the user's answer as a new decision for it and, if sift had changed the message in Gmail, takes that change back so the new decision is carried out from where the message started.
- **A waiting suggestion follows the rules and labels as they are now.** When a rule or a label changes in the dashboard, each waiting suggestion is run through the rules again, with no model (`src/learn/redecide.ts`), and a new decision is recorded where the answer differs: a rule of the user's now decides it, so it stops being a suggestion; its label now does something else, so the same label is recorded with the new outcome (and mail is never newly hidden from a sender who was not checked); or the rule that had decided it is gone, so it goes back to what a tier said before, or to review. What a model decided, worked out again, keeps that call's run and the rule it was shown. Mail the user answered for is never touched, even by an answer given while this runs: it is one transaction, and each message is checked again, its decision row locked, just before its new decision is recorded. Mail a rule decided when it arrived stays as history.
- **Every marked message becomes an example.** The answer creates an `examples` row and deletes the message's `suggestion_bodies` text; the next pass of `sift run` fetches its readable text into the example. These are the evaluation and training set. A message that has since been deleted keeps its answer and is marked gone.
- **Gmail teaches too.** Each sync reads what the user did to messages sift has decided (`learnFromGmail`, `src/learn/gmail.ts`), and records it as the "only this one" answer is recorded, marked `via = gmail` in `feedback`:
  - Where the message is now, read fresh, is the outcome the user wants. A move does not say what the mail is, so the label sift gave stands (and counts as right) and the outcome is recorded as the exception; a different `sift/…` label put on it is a correction of the label.
  - The new decision is the user's (`by_user`) but is not carried out, whether or not sift is on, so sift does not then move a message the user has just placed.
  - While sift is off, the user doing in Gmail what sift suggested counts as agreeing.
  - Skipped: mail sift could not place and the user did not label (there is no label to record), trashed or deleted mail, and mail sift never recorded.
  - The same history read twice records nothing new: an answer is only recorded when the message's place and label differ from its current decision and from the answer already on it.
  - Not seen: anything done while the history cursor was expired.

- **Examples are kept until the user deletes them**, one at a time or all of an account's, or for 365 days after the answer (`EXAMPLE_KEEP_DAYS`, `src/store/examples.ts`); `sift run` deletes the ones past it when it starts and once a day. Deleting an example removes the stored message only: the answer stays in `feedback`, and any rule it made stays a rule.
- **Examples test the model.** A test run replays the model over an account's stored examples and scores it against the user's answers: right, wrong, "unsure" and failed calls overall and per label, which labels were taken for which, and cost and tokens per message. It is started from the dashboard and never by sift itself, because every example is a paid model call; a run takes at most 200 examples, newest answers first, four calls at a time, in the background. Each example is judged on what is stored (the recorded headers, the example's text, the sender's history as it stood before the message's first decision), so Gmail is not asked and the user's later answer does not leak in. A run records what it ran with (model, a hash each of the prompt layout and the labels, and whether examples were shown) and one row per example, so two runs can be compared example by example. With examples shown, the one under test is left out of its own prompt; answers that still had another example from the same sender are counted apart, since they are easier than new mail.

Code: `src/learn/feedback.ts` (suggestions, answers, accuracy), `src/learn/gmail.ts` (telling the user's changes from sift's, answers from Gmail), `src/daemon/examples.ts` (capture), `src/learn/evals.ts` and `src/triage/score.ts` (test runs).

## State

One Postgres database for everyone: Postgres is the one engine Vercel, Cloudflare and a local install all have. Locally it is PGlite, Postgres compiled to WebAssembly and run inside sift, keeping its data in `database/` in the home directory; given a Postgres server's address (`DATABASE_URL`, or `database.url` in `sift.toml`), sift uses that instead. Given also the address of the role that owns the tables (`DATABASE_MIGRATION_URL`, `database.migration_url`), sift migrates as that role, grants `sift_app` to the first, and runs as it: a role that owns nothing cannot change the tables or turn their policies off.

- **Schema and migrations.** The schema is `src/store/schema.ts` (Drizzle). `pnpm db:generate` writes each change as a migration in `src/store/migrations/`, which sift applies when it opens the database (Drizzle's migrator); what Drizzle cannot say (grants, `FORCE ROW LEVEL SECURITY`) is a custom migration made the same way (`drizzle-kit generate --custom`). A test fails when the schema has a change no migration covers. A database last opened by a newer sift is refused. Drizzle orders migrations by when they were made, so when two branches each add one, generate again on the merged branch rather than keep both.
- **Who sees what.** `users` and `accounts` say who the people are and which mailboxes are whose. Every other table holds one person's data: it carries `user_id`, filled in from the transaction's `sift.user` setting, and has row-level security, forced even for the tables' owner, that shows and accepts only that person's rows. Foreign keys include `user_id`, so no row can point at another person's. Every query runs in a transaction that first becomes `sift_app`, a role that owns nothing and cannot bypass the policies (`handle`, `src/store/sql.ts`): the central handle sees no one's rows, `store.user(id)` only that person's, `store.nobody` nothing. That is the second line. The first is sift's own code: the handle's query builder (`src/store/own.ts`) adds `user_id = <person>` to every select, join, update and delete of a person's table, puts the person's id on every row inserted, refuses a `user_id` from the caller and a right or full join, and the central handle refuses a person's table outright. Tests check every such table has the policy, that one person cannot read or write another's rows, and that the builder holds them apart with row-level security out of the way (`tests/own.test.ts`). Locally PGlite runs as a superuser, so a statement that resets the role would escape the policies; sift sends only what its builder makes. With a server, connect as a role that is not a superuser. See [SECURITY.md](SECURITY.md).
- **One process.** PGlite is one process's alone and does not check that itself, so sift holds `database.lock` (its process id) and refuses the folder to another process while it is alive; `sift status` then says sift is running. A lock left by a process that has gone is taken over.
- **Queries** are built with Drizzle's builder on the `Sql` handle, from the tables, operators and `sql` in `src/store/query.ts`; nothing outside `src/store/` imports Drizzle, and no SQL text names a table (`sql` refuses one interpolated, and a test reads `src/` for one written). `sql` is for expressions the builder lacks (`count(*) FILTER`, `coalesce`), with columns interpolated. A transaction is one call taking a function that awaits nothing but the database, since it holds the connection; using an outer handle inside it is refused rather than left to wait on itself. A failed statement reports the database's error, never the values bound to it, which can be a message's text.

Defaults are written by code, never by a migration: a mailbox's starting labels with the mailbox (`ensureMailbox`), and a person's preferences when their database is first opened. Labels are never deleted, so every label a row names exists. Together the tables are the complete record of what sift saw and did, and everything else (the dashboard, undo, future analytics) reads from them.

- **messages:** one row per message sift has seen: sender, recipients, subject, the triage headers, the labels at sync time and the facts derived from them. No body. This is enough to triage a message again without refetching it.
- **feedback, examples:** the user's answers, one per decision (what the mail is, what should happen to it, and whether it came from the dashboard or Gmail), and the readable text of each message they answered for, kept as evaluation and training data until deleted or a year old (see Teaching).
- **suggestion_bodies:** the readable text of mail still waiting on the user, so a suggestion can be judged by reading it: its start is shown under the subject in the Suggestions list, read from here and not stored again. Held only for mail sift would move or could not place, and deleted when the message is answered (in the answer's own transaction) or stops being a suggestion, and after 30 days regardless, which `sift run` checks once a day for everyone whether or not Gmail can be reached (`src/daemon/bodies.ts`, `purgeSuggestionBodies`). These two tables are the only places message content is stored.
- **model_runs:** every call to the model about a message, judged or failed, with the model, tokens, dollars, when it started and finished, and the error when it failed. Cost is summed from here, so a call that failed (an unusable answer is still billed) counts. Runs no decision links to are how a message's tries are counted; putting it back in the queue, or an outage, marks them `retried_at` rather than deleting them.
- **decisions:** an append-only log. Each is a suggestion or to be carried out (`carry_out`), says whether it is the user's own answer (`by_user`), and has an outcome once carried out; it is unsettled while `carry_out` and no outcome. Every triage outcome is recorded, including "keep" and "could not decide" (a model unsure), but not a failed model call, and not mail no tier looked at for want of a model, both of which stay queued. Each has the tier that made it, the reason, the confidence, how long deciding took, and the run that reached it when a model was asked. A message can have several decisions; the latest is current.
- **actions:** the audit log of every mailbox change, with labels before and after, linked to the decision it carried out. Creating and removing a Gmail filter is logged here too, with no message.
- **eval_runs, eval_results:** each test run of the model over the examples, with its settings, and what the model said for each example. Labels and costs only, no message content.
- **labels, rules, mailboxes:** what mail can be, what sift knows without a model, and each mailbox's history cursor and last sync time.

**Retention.** `sift run` deletes, on its first pass and once a day, each message that nothing has happened to for 365 days, with its decisions, actions, model runs and answers (`RETENTION_DAYS`, `src/daemon/retention.ts`; well past sync's 7-day recovery search, which could otherwise bring back a message already forgotten). Keys into `messages`, `decisions` and `model_runs` do not cascade, so `pruneOld` names what it deletes and a new table that references them fails the prune until it is added there. What it costs: a change older than the window can no longer be undone from sift, and the model is told less about how much a sender has sent. A message is kept, however old:

- while it waits in the queue to be decided. Mail the model ran out of tries on is not waiting: once its last try is as old, it goes;
- while its example is kept. Once the example is deleted or a year old, the message and its answer go like any other;
- while a decision for it waits to be carried out, or a change to it was never confirmed;
- while it holds the record of an unsubscribe, which is how sift knows not to ask that sender again.

A suggestion still waiting is spared for 365 days from its decision, like any decision, and no longer.

Not per message, and kept until removed: labels, rules, proposals, correspondents, test runs, preferences, mailboxes and sign-ins (`credentials`). Removing a mailbox or deleting a person removes all of theirs (see Deleting).

Postgres reuses the freed space; the files do not shrink.

**Deleting.** Removing a mailbox and deleting a person are each one statement (`removeMailbox`, `deleteUser`, `src/store/accounts.ts`). Every table with an `account_id` has a key to `mailboxes` that cascades, and `mailboxes` one to `accounts`, so deleting the `accounts` row takes every row of that mailbox; every table with a `user_id` cascades from `users`. A test fails when a table with an `account_id` lacks the cascading key. The mailbox's Gmail sign-in is revoked at Google first (`Controls.revokeGmail`); failing to reach Google does not stop the removal, and the person is told. Then its token is deleted from `credentials`, then the account. Deleting a person does that for each of their mailboxes and deletes the `users` row, model sign-ins included. A person's only mailbox is how they sign in, so it is never removed on its own: the page disables its trash can and the server refuses; deleting the account is its own step. When the owner is deleted, the earliest person left owns the install; with nobody left, whoever signs in next does. Gmail filters sift wrote stay in Gmail, and its labels stay on mail. A pass that reaches a mailbox or person deleted meanwhile skips it without reporting it, and the run loop forgets them.

### Dashboard

The dashboard is where the user watches sift, teaches it and manages it. `sift run` serves it (a JSON API in `src/dashboard/` and the static web app built from `web/`) from the same process that reads and classifies mail; `sift dashboard` serves it alone.

**Who may use it**

- **Someone signed in with Google as a connected account.** One sign-in does both jobs: it gives sift its access to the account (the Gmail scopes and a refresh token) and it proves the viewer owns that account. There is no separate login and no terminal step. The page's static files are public; every `/api/` route needs the session. So are `/terms` and `/privacy` (`web/src/views/legal.tsx`), which Google reads before it lets anyone outside the test list sign in; the sign-in screen links to both. They speak for whoever runs the install, and what they say sift reads, keeps and sends must stay true when that changes.
- **Users and their mailboxes.** A user is a person; an account is one of their mailboxes, an identity they signed in with (`users`, `accounts.user_id`). The first sign-in makes the first user, who owns the install. Someone signed in can connect another mailbox (Settings), which becomes theirs. An account never changes hands.
- **Each person sees only their own.** A request is given the database of whoever is signed in, whichever of their mailboxes they signed in as, and no other. The dashboard is handed `People` (`src/store/people.ts`), not the store: it finds a person by the address of their session, and opens a database only through that person's `open(id)`, which refuses any id they may not read (today, any but their own). A view of all of a person's mailboxes, such as their suggestions, is one query, since their mailboxes share their database; one that merged several people's would open each through `ctx.open`; its scope is their mailboxes (`src/dashboard/scope.ts`). Every query also takes the scope and filters by it, and `?mailbox=` on any read narrows it to one of them. Every write says whose data it touches and is refused, as if the thing were not there, when that is someone else's; a row named by id is looked for only in the requester's database, so another person's gets the answer one that never existed would. What applies to the whole install (pulling in older mail) only the owner may change; whether sift is on for them, their model and its sign-in, and removing their own mailboxes or deleting their account are each person's own (`touches: 'self'`, or the mailbox). With no sign-in set up (tests, tools) the request is the owner's.
- **An allow list is who the install is for.** When `dashboard.allow` in `sift.toml` lists addresses (a step in `sift init`), no other Google account can sign in, the first included, and a session ends when its address is taken off the list. It is read on every request. A listed address sift does not know may sign in by itself, and is then a person of their own. Without a list only the first account, and mailboxes added by someone signed in, can ever sign in. The list limits the dashboard only: an account left off it stays connected and its mail is still classified.
- **Sessions** are a signed cookie (HMAC with a per-install secret in `dashboard-key`), HttpOnly, SameSite=Lax, 30 days, naming the mailbox and the person. A session stops working when its mailbox is removed, and is refused if the address has since been connected again by someone else. Removing the mailbox one is signed in as clears the cookie.
- **Google's constraint.** It returns a browser only to `localhost` or an HTTPS address on a real domain. So the dashboard is used at `http://localhost:8787`, or over Tailscale at `https://<machine>.<tailnet>.ts.net` (`tailscale serve` proxies to localhost and passes the original scheme in a header, which is believed only from this machine). At a plain hostname or address the page says where to go. The Google client must be a "Web application" one listing `<origin>/auth/callback` for each address. A Desktop app client is refused.
- **Host and origin checks.** It answers only to names and addresses that are this machine (blocking DNS rebinding), and every write must come from the dashboard's own page: its Origin, a JSON content type and a custom header.

**What it may do**

Everything that manages sift: answer suggestions, turn sift on or off for the viewer's own mail, choose the model, add and edit labels and what happens to each, add and remove rules, write a rule to Gmail as a filter or take it out, undo a mailbox change, try a failed change again (the decision's outcome is cleared and the next pass acts on it, `POST /api/decisions/retry`), put mail the model could not judge back in the queue (`POST /api/unjudged/retry`, or all of it, `POST /api/unjudged/retry-all`), pull in older mail, and trigger a check.

- It changes the database directly, never `sift.toml`. A pass reads each person's choices as it reaches their mail, and a change wakes it, so nothing needs restarting.
- It never imports Gmail, the executor or the daemon (lint enforces this). The few things that need them (signing in, undo, Gmail filters, pulling in older mail, check now, a test run of the model) are passed in by the process as `SignIn` and `Controls` (`src/dashboard/controls.ts`), so every mailbox change still goes through the executor and the audit log.

**What it counts.** Messages, not decisions: a message is counted once, where sift first decided it, so an answer or a decision made again after a rule changed does not count it twice. "Without a model" is those sift first decided with no model call (not the user's own answer); a model's cost is "for" every message it was asked about, failed calls included. Failed, in Activity, is a change that failed or was never confirmed; one still waiting for a pass (an answer, or anything left while sift was off) shows as waiting, among the changes.

**Older mail.** Pulling in the last N days records those messages as suggest-only. They are decided on the next pass and are never acted on, even when sift is on.

**The page**

- **Untrusted content.** Subjects and sender names come from email. React renders them as text, and the page is served with a content security policy that allows no inline script, no inline style and nothing from another origin.
- **A message as its HTML.** The message panel shows the text sift holds, or, chosen per browser (`localStorage`), the message's HTML in a frame. The page never holds that HTML: the frame loads `GET /api/message/html`, which checks the message is one of the viewer's own recorded ones, has `Controls.messageHtml` fetch the HTML part from Gmail (`format=full`, the first `text/html` part), cleans it (`src/dashboard/mail-html.ts`) and sends it; nothing of it is stored or logged, and it is fetched again each time it is shown. Its response has its own policy: `sandbox` with only `allow-popups allow-popups-to-escape-sandbox` (no script, no origin of its own), `default-src 'none'` with inline styles and `data:` images and fonts only, `frame-ancestors 'self'`, no referrer, no DNS prefetch. So no image, font, stylesheet or tracking pixel loads from anywhere. The cleaner is the second wall: it rebuilds the document from the tags it read, dropping scripts, frames, objects, forms, `base`, `meta`, `link`, svg, event handlers and any link that is not `http(s):` or `mailto:`, and opens every link in a new tab with `rel="noopener noreferrer"`. It drops remote `src`, `srcset` and `background` itself and leaves CSS `url(...)` to the policy, which catches every spelling. The page's own policy gains only `frame-src 'self'` for it. The toggle is offered unless sift has read the whole message and found no HTML part (`hasHtml` false); for mail it never read (a rule placed it), the frame says when there is none.
- **Stack.** React and Tailwind, with sift's own design system (`web/src/system`, [DESIGN.md](DESIGN.md)). Behaviour that is hard to get right (the select's list, the drawer's focus trap) comes from Base UI's unstyled primitives, wrapped inside the system's parts so no screen imports them; the look is all sift's. Base UI's style injection is turned off in `main.tsx` for the content security policy, with its one rule moved into `index.css`. The chart is drawn by the system itself, so there is no chart library.
- **Data.** `web/src/lib/api.ts` is the only file that talks to `/api/`. Reads go through TanStack Query: cached in memory only (mail data is never written to the browser's storage), refreshed on an interval, on returning to the tab and after any change made from the page. A request that gets no answer marks sift unreachable: the masthead says so, every query pauses with what it last loaded, and the page asks again until something answers, then refreshes. While unreachable a change is refused where it was made, never queued, so nothing happens later that the user did not see.
- **Addresses.** Sections are paths (`/rules`, `/activity`). The server answers any path that names no file with the one page, which reads the path and moves between sections with the History API (`web/src/lib/route.ts`); nothing is rendered on the server. Search text, filters and the open message are in the query, so a view can be bookmarked and Back closes the message panel. Typing and stepping through a list rewrite the current history entry; only opening a message adds one. Links from when sections were fragments (`/#rules`) are rewritten on load.
- **Code.** The page is client-rendered. Libraries are built into files of their own (`react`, `vendor`) so a new build of sift leaves them cached; the home page comes with the app, and every other screen is its own file, fetched when first needed and ahead of need once the page is idle. Server rendering was tried on a branch (React Router 8, 2026-11-15) and declined: see TODO.md.
- **Installed.** The page has a web manifest and a service worker, so it can be installed on a phone or a desktop. The worker (`web/src/sw.js`, written to `/sw.js` by the build with the list of files to keep) keeps only the page's own files: the document, its script and style, and fonts. It never handles `/api/`, `/auth/` or `/dev/`, so no mail data is ever kept in the browser. A navigation goes to the server first and falls back to the kept page, which then finds sift unreachable and says so. The policy allows the manifest and the worker from this server only (`manifest-src`, `worker-src`). Both are served without a session, like the rest of the page's files. The page does not register the worker under `sift dev`, and removes one left by `sift run` at the same address. A service worker needs a secure context: `localhost` or the HTTPS address, not a plain-HTTP LAN name.
- **Look.** See [DESIGN.md](DESIGN.md). Tiers are one ink that thins as cost rises, because they are an ordered cascade.
- **Developing.** `sift dev` runs `sift run` under Node's watch mode beside a watching build of the page. In that mode the server reads the page's files afresh on each request and adds one script of its own, which reloads the page when the build changes or the server restarts. It is not hot module replacement: that would need inline script, and keeping the real content security policy while developing is worth more than keeping component state.
- **Layout.** `server.ts` is a web handler, `Request` to `Response`, and is what applies to every request: the Host check, the session, the scope and the checks on writes. It does not serve the page's files: `sift run`'s `node:http` adapter (`src/cli/serve.ts`) does, and hands it everything else with the peer address, which a `Request` lacks and the forwarded-scheme rule needs. Each route is in `api/`, one module per resource, as a `Read` or a `Write` that declares its path and, for a write, whose data it touches, or a `Frame`, a read answered with a document for a frame under `FRAME_HEADERS`. What they read from the database is in `queries/`, laid out the same way.
- **Shared types.** `src/dashboard/types.ts` defines the API's JSON and has no imports, so the web app imports it directly.
- **Vercel's UI SDK** (`@ui-sdk/react`, announced 2026-11-12) was evaluated and not adopted yet: it is a 0.1 beta, and it injects a runtime `<style>` by default. It would do the job Base UI does now, supplying behaviour under the system's parts. Because only `web/src/system` imports the primitives, moving to it later changes those few files and no screen.

## Unsubscribing

Gmail has no API for it, so sift makes the request a mail client would: the sender's one-click address (RFC 8058), a single POST. Unsubscribing is an extra a label or a rule carries, like marking read; the default labels for bulk mail have it on. It is never a button. The daemon makes the request after the decision's mailbox change has gone through, only while sift is on, and never for a sender the user has written to. It is recorded as an action before the request, never repeated for a sender it worked for, and not retried for a week for one it failed for. The address comes from the email, so it is used only if the message passed DMARC, the address is plain HTTPS on the standard port, and it resolves to the public internet; the connection is made to the address that was checked, and a redirect is not followed. Lists that can only be left by sending an email are refused, since sift cannot send. Code: `src/actions/unsubscribe.ts`.
